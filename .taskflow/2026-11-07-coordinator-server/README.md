## 1. Проблема

`runner-manager` сейчас полностью локальный: каждый хост сам опрашивает GitHub REST и сам решает,
поднимать ли JIT-раннер. Это осознанное решение (нет входящих портов, нет сервера), и оно работает,
но у него три цены:

1. **Задержка старта.** Активный репозиторий опрашивается раз в 60 с (`host set-poll-interval
   --active`, пол 30 с), простаивающий — раз в 10 с (условные запросы, `304` бесплатны). Новый job в
   репозитории, где уже что-то идёт, может ждать до минуты, хотя свободная машина есть.
2. **Общий лимит.** Все хосты, вошедшие под одним GitHub-пользователем, тратят **одну** корзину
   5 000 запросов/час (плюс 900 points/min secondary limit). Пять машин × N репозиториев опрашивают
   одно и то же пять раз. Отсюда 60 с.
3. **Нет общей картины.** Хост не знает о соседях. Если две машины обслуживают один label, обе
   поднимают раннер, один из них уходит `ExitedIdleWithoutWork` (лишний холодный старт). Тяжёлый job
   может попасть на M1 с 8 ГБ, пока Linux на 64 ГБ простаивает.

## 2. Цель

Необязательный компонент **Coordinator** — маленький сервер, к которому хосты подключаются по
исходящему WebSocket, если в локальных настройках указан его URL. Без него всё работает как сейчас.

Coordinator:

- получает события GitHub **вебхуками** (`workflow_job`) и мгновенно будит нужный хост;
- знает в реальном времени состояние каждого хоста (свободные слоты, CPU/RAM, тёплые кэши);
- **запоминает, насколько тяжёл каждый job** по прошлым запускам, и выбирает хост с учётом этого;
- пускает к себе только авторизованные хосты.

Не-цели: заменять локальную логику безопасности и лимитов хоста; хранить GitHub-секреты хостов;
быть обязательным.

## 4. Архитектура

```text
            GitHub  ── webhook workflow_job (HMAC) ──►  Coordinator (публичный HTTPS)
               ▲                                         │  ▲
               │ JIT / REST (токен хоста)                │  │ wss:// (исходящее от хоста)
               │                                         ▼  │
   ┌───────────┴──────────┬──────────────┬──────────────┬───┴─────────┐
   win-big            win-small        mac-new         mac-m1       linux
   runner-manager     runner-manager   ...
```

Ключевой принцип: **Coordinator советует, хост решает.** Coordinator присылает «запусти раннер
для target X, profile Y». Хост, как и сейчас, проверяет свою политику, `max_capacity`, host capacity,
`host doctor`, и сам вызывает `generate-jitconfig` своим токеном. JIT-конфиг никогда не проходит
через Coordinator. Взлом Coordinator в худшем случае заставит хосты поднять лишние раннеры в рамках
их собственных лимитов, но не даст ни токенов, ни кода.

### 4.1 Режимы работы хоста

| Режим | Когда | Поведение |
|---|---|---|
| `standalone` | URL не задан (по умолчанию) | Как сейчас. |
| `coordinated` | Есть живое WebSocket-соединение | Локальный опрос замедляется до редкой страховочной сверки (например раз в 5 мин); старт по команде Coordinator. |
| `fallback` | URL задан, но связи нет N секунд | Автоматически возвращается к обычному опросу 10/60 с. При восстановлении связи — обратно. |

Хост никогда не простаивает из-за упавшего Coordinator.

### 4.2 Источник событий

1. **Вебхук `workflow_job`** (`queued`, `in_progress`, `completed`). В payload есть `labels`,
   `workflow_name`, `name` (job), `run_id`, `run_attempt`, `runner_name`, время начала/окончания —
   ровно то, что нужно для маршрутизации и статистики.
2. **Страховочная сверка.** Вебхуки могут теряться. Coordinator сам (одним токеном, а не пятью)
   раз в 1–5 мин сверяет очередь условными запросами. Это всё равно на порядок дешевле, чем сейчас.
3. **Подключение вебхука.** Варианты (см. открытые вопросы): вручную на репозиторий/организацию с
   секретом; автоматически через API (`admin:repo_hook`, т. е. новое разрешение App); или отдельный
   собственный GitHub App, чей webhook URL указывает на Coordinator. Вебхук общего App
   `runner-manager` для self-hosted Coordinator не подходит: его URL один на всех пользователей.

### 4.3 Протокол хост ↔ Coordinator (WebSocket, JSON, версионированный)

От хоста:

- `hello` — версия протокола, host id, ОС/арх, ядра, RAM, диск, список targets/profiles и их labels,
  тёплые кэши (git cache, persistent slots по репозиториям).
- `heartbeat` (каждые 5–10 с) — занятые/свободные слоты, загрузка CPU, свободная RAM, свободный диск,
  `host_unfit`, состояние draining/update.
- `attempt_started` / `attempt_finished` — job, runner name, длительность, **пиковые CPU/RAM
  дерева процессов**, исход (успех, отмена, `ExitedIdleWithoutWork`).

От Coordinator:

- `launch` — target, profile, `job_key`, `lease_id`, срок годности.
- `cancel_launch` — job взят другим хостом или отменён.
- `config` — интервал heartbeat, интервал страховочной сверки.

Хост отвечает `launch_ack` (принял / отказал с причиной: нет слота, unfit, политика выключена).
Отказ — сигнал Coordinator выбрать другой хост.

### 4.4 Важное ограничение GitHub: раннер нельзя привязать к конкретному job

JIT-раннер берёт **любой** queued job с подходящими labels, а не тот, ради которого его подняли.
Поэтому планирование идёт на уровне «сколько раннеров какого профиля и на каком хосте», а
статистика тяжести применяется к **очереди** job'ов этого label. Практические следствия:

- Чтобы Coordinator мог выбирать между машинами, им нужен **общий label пула** (например
  `rm-pool-win`, `rm-pool-linux`), а не только уникальный label хоста `rm-home-win-x64`. Workflow
  пишет `runs-on: rm-pool-linux`, Coordinator решает, какой хост поднимает раннер.
- Для job'ов, которые обязаны идти на конкретную машину, остаётся label хоста — как сейчас.
- Для тяжёлых job'ов можно ввести классы пула (`rm-pool-linux-heavy`), которые Coordinator
  поднимает только на машинах с достаточной RAM. Это надёжнее, чем угадывать, какой job заберёт
  раннер.
- Без Coordinator общий label у нескольких хостов даёт сегодняшнее поведение: оба поднимают раннер,
  лишний уходит по idle timeout. С Coordinator раннер поднимает ровно один хост.

### 4.5 Планировщик

На каждый queued job (или пачку):

1. Отобрать хосты, у которых есть подходящий профиль (ОС, labels, enabled) и свободный слот.
2. Оценить требования job'а по истории: `p90(peak_ram)`, `p90(cpu)`, `p50(duration)` по ключу
   `repo + job name` (матрица — с учётом значений, если различимы; без workflow: см. 8.1). Нет истории — класс
   «неизвестно», оценка по умолчанию для репозитория.
3. Отсечь хосты, где оценка RAM не влезает в свободную память с запасом.
4. Ранжировать по сумме весов:
   - **тёплый кэш / persistent slot** этого репозитория (самый большой выигрыш);
   - запас ресурсов после размещения (не забивать машину до упора);
   - скорость машины для этого job'а (историческая длительность на этом хосте);
   - «не занимать большую машину лёгким job'ом, если она может понадобиться тяжёлому».
5. Отправить `launch`, ждать `launch_ack` с таймаутом, при отказе — следующий хост.
6. Вебхук `in_progress` с `runner_name` подтверждает, чей раннер взял job; `completed` закрывает
   учёт.

Первая версия может быть простой (фильтр + тёплый кэш + наибольший запас RAM), веса — позже.

### 4.6 Статистика тяжести job'ов

- Хост измеряет пиковые CPU/RAM/диск дерева процессов `Runner.Listener` (Job Object на Windows,
  cgroup на Linux, опрос дерева процессов на macOS) и длительность.
- Coordinator хранит записи в SQLite, агрегаты — скользящие перцентили за последние N запусков
  (старые данные устаревают: job'ы меняются).
- Видно через CLI/TUI (`runner-manager coordinator stats`): топ тяжёлых job'ов, распределение по
  хостам, сколько времени сэкономлено против опроса.

## 5. Авторизация и безопасность

Coordinator торчит в интернет, поэтому три независимых периметра:

1. **Хост → Coordinator.**
   - Только `wss://` (TLS).
   - Регистрация хоста одноразовым кодом: админ выполняет `coordinator host invite` →
     короткоживущий код; на хосте `runner-manager coordinator join URL --code XXXX`.
   - При join хост генерирует пару ключей Ed25519, приватный ключ лежит в том же системном
     хранилище секретов, что и GitHub-credential (Keychain / Credential Manager / machine store).
     Coordinator хранит только публичный ключ.
   - Каждое подключение — challenge-response подписью (nonce от сервера), никаких долгоживущих
     bearer-токенов в конфиге.
   - Отзыв хоста одной командой; отозванный ключ рвёт соединение сразу.
2. **GitHub → Coordinator.** Проверка `X-Hub-Signature-256` (HMAC секретом вебхука), отбрасывание
   повторов по `X-GitHub-Delivery`, лимит размера тела. Неподписанные запросы — `401` без деталей.
3. **Владелец → Coordinator (администрирование).** Веб-интерфейса нет (D5). Админ-команды
   (`host invite`, `host revoke`, `stats`) идут либо через CLI на самом VPS, либо с машины
   владельца по тому же WSS с отдельным админ-ключом Ed25519, выданным при установке. Анонимного
   доступа нет; публично открыты только `/webhook` (с HMAC) и `/connect` (с подписью хоста).

Дополнительно:

- Coordinator не получает и не хранит JIT-конфиги, GitHub-токены хостов, логи job'ов, исходники.
- Хост проверяет каждую команду `launch` против своей локальной политики; Coordinator не может
  включить выключенный профиль, превысить capacity или обойти `host_unfit`.
- Rate limit на соединения и сообщения, защита от повторов `lease_id`.
- Правило репозитория остаётся: fork/untrusted PR на личных машинах — только осознанно.

## 7. Изменения в runner-manager (клиент)

- Настройка: `runner-manager coordinator join URL --code …`, `coordinator status`,
  `coordinator leave`; поле в TUI (Host Settings).
- Новый источник спроса в `reconcile`: команда `launch` эквивалентна «demand = 1 для этого
  профиля», но проходит через тот же `HostAllocator` и те же потолки.
- Расписание опроса учитывает режим `coordinated`/`fallback`.
- Измерение пиковых ресурсов attempt'а и отправка в `attempt_finished`.
- Общие labels пула в профилях (уже поддерживается механизмом labels, нужна только договорённость
  об именах и проверка неоднозначности с учётом Coordinator).
- `status`/`host doctor`: состояние связи с Coordinator, последнее событие, режим.

### 8.1 Отклонения от исходного замысла

- **Отзыв хоста (5.1).** «Отозванный ключ рвёт соединение сразу» реализовано так: админ-CLI —
  отдельный процесс над тем же SQLite, сервер раз в 500 мс читает `PRAGMA data_version` (меняется
  только от чужого коммита, без запроса) и закрывает соединения отозванных хостов — то есть не
  мгновенно, а в пределах ≤1 с. Админского эндпоинта для сигнала нет намеренно.
- **Режим launch требует покрытия App (4.1, 4.4).** Хост в `coordinated` (и, значит, получающий
  `launch` вместо собственного спроса) — только если страховочная сверка через GitHub App
  Coordinator'а покрывает этот target. Без App или без доступа к репозиторию хост в `fallback`
  и считает спрос сам; пул-профиль тогда ведёт себя как обычный.
- **Идентичность job'а для учёта очереди = репозиторий + labels (4.4, 4.5).** Лизы и очередь
  считаются по ключу «репозиторий + обязательные labels», а не по конкретному job: раннер всё
  равно возьмёт любой подходящий job. Имя job'а (`repo/job`) используется только для
  статистики и оценки тяжести очереди (её самый тяжёлый job).
- **Ключ статистики без workflow (0.4.48).** `workflow_name` у job'а в API GitHub — это заголовок
  запуска (`run-name`), он другой при каждом запуске, поэтому ключ — `repo/job`. Цена: одноимённые
  job'ы разных workflow одного репозитория делят статистику. Фильтруют хосты только собственные
  замеры job'а; p90 репозитория для незамеренного job'а только ранжирует.
- **Этап 4.** Тяжесть очереди — максимум p90 пиковой RAM среди её job'ов; неизвестный job —
  p90 репозитория, иначе глобальное значение по умолчанию (2 ГиБ), и при отсутствии данных
  фильтр по RAM не применяется (порядок как на этапе 3). Длительность job'а — с 0.4.47
  `started_at`→`completed_at` вебхука (в 0.4.45–0.4.46 была длительность attempt'а хоста с запуском
  раннера, ожиданием и очисткой: 14-секундный job выглядел как минута); длительность attempt'а —
  только запасной вариант, если `completed` не пришёл за 2 мин. Ожидание в очереди
  (`created_at`→`started_at`) хранится отдельно и показывается p50/p90. Рост диска
  workspace не измеряется (обход checkout'а каждые 2 с не дёшев). Windows: нативные раннеры не
  запускаются в Job Object, поэтому вместо его учёта — снимок дерева процессов (Toolhelp +
  `GetProcessMemoryInfo`/`GetProcessTimes`); Linux — `/proc`, а не cgroup (отдельной cgroup у
  нативного раннера нет). «Сколько времени сэкономлено против опроса» в `stats` не считается:
  вместо этого показаны счётчики launch'ей и wake'ов.
- **Запуск вне блокировки хоста (0.4.49).** Под блокировкой остаётся только резервирование:
  решение аллокатора и запись `Allocated` в журнал. Пакет, регистрация и процесс — вне неё,
  параллельно (cores/4, минимум 2), поэтому потолки считаются как раньше, а упавший демон оставляет
  запись, которую закрывает восстановление при старте. Запись о доверии к дереву пакета — одна на
  все target'ы демона: по записи на target каждое переключение между ними стоило полной закачки.
  Первый запуск после старта демона скачивает пакет заново: это решение безопасности, пул готовых
  раннеров — отдельная задача. Launch с поднимающимся раннером не истекает до 15 мин, и heartbeat
  продлевает его лиз; 45 с считаются от настоящего отказа запуска. Порядок «старые первыми» между
  target'ами — в пределах 2 с ожидания: цикл старшего может быть занят.

- **Пул `rm-pool-any`, CPU и диск (0.4.52).** К трём пулам по ОС (D10) добавлен
  ОС-независимый `rm-pool-any`: его может нести профиль хоста любой ОС (рядом со своим пулом ОС
  или вместо него), кандидаты — все такие хосты, выбор — обычной оценкой и статистикой.
  Хост направляет такой профиль запусками, только если Coordinator в `hello_ack` сообщил
  `any_pool`. Загрузка CPU из heartbeat даёт слагаемое `cpu` (свободные ядра); хост с загрузкой
  ≥ 90 % или со свободным местом на томе runner root < 10 ГиБ (теперь в каждом heartbeat) —
  крайний вариант: берётся, только если больше некому.
